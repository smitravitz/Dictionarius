FM-index for Dictionarius — viable?

✅ Viable — and strongly differentiated.

Benchmarked on 370,105 real English words. Engineered FM-index is ~8× smaller than SQLite FTS5 trigram for the same substring search, and faster. No findable open dictionary app uses this — the algorithm itself is mature (DNA aligners, search engines).

Verdict: the entire open dictionary ecosystem uses "compress data blocks + a separate sorted/prefix key index." Substring, when offered at all, is a slow scan (GoldenDict) or a heavy separate inverted index (Xapian in ZIM). None uses a compressed self-index. FM-index is proven elsewhere — DNA aligners (BWA, Bowtie), full-text search — with mature libraries (sdsl-lite, rust fm-index, Python shellinford). So: low algorithmic risk, high product novelty.

Honest risks ⚠️

  • Engineered size is modeled, not built. Measured naive = 8.7 MB (already beats trigram); the ~2.5 MB rests on RRR/wavelet-tree results. Confirm with a real library before committing.
  • Web target needs wasm. No JS-native FM-index; you'd compile one (sdsl/rust→wasm) or ship a wasm build. Extra toolchain.
  • Build is server-side and heavy (suffix array construction), but one-time — the shipped index is cheap to open.
  • Locate needs a small extra structure (sampled SA or the separator-rank trick used here) — already in the size model.
  • Glosses are a separate problem. FM-index solves headword mid-word search; definition text stays in zstd-compressed blocks with offset lookup.

Recommendation

Prototype it for real behind the existing seam — don't rewrite anything yet.

The getCandidates seam from the architecture review is exactly the plug point: build one real FmIndexSource adapter with a proven library, run it against the same contract test as the SQLite and mock sources, and measure the engineered size for real. If it lands near ~10 MB at full scale, it becomes the core substring engine and the trigram add-on is unnecessary. Low commitment: one adapter behind a seam that already exists.
